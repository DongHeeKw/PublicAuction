# Product Requirements — PublicAuction (v0.1)

## 1. 문제·고객·가설
- 온비드 공매 공고는 자료가 분산되어 있어 물건 유형/지역/기간/결과를 비교하기 번거롭다.
- 주요 사용자: 공개 공매 정보를 확인하려는 일반 탐색자, 반복 검색하는 업무 사용자, 차량/동산 전문 정보 수요자.
- 가설 H1: 유형별 공매 결과와 검증 가능한 공고 카드가 탐색시간을 줄인다.
- H2: 인기 카테고리 + 정확한 필터가 첫 방문에서 상세열람률을 높인다.
- H3: 과거 결과·주의사항이 반복 방문을 만든다. FOMO, 가상의 할인율, 잭팟 심리를 자극하지 않는다.

## 3. 홈페이지 정보구조
Hero: 검색 + '공공자산을 데이터로 비교하세요'. 아래: **인기 품목(관측된 과거 데이터)**, 신규 등록, 지역별 탐색, 마감 일정, 분석 설명, 안전 이용 안내. 인기도가 높아도 가격 우위·수익 기회를 보장하지 않는다.

## 4. 핵심 사용자 플로우
검색 → 유형 카드 → 필터 → 상세/원본·주의사항 → 공식 온비드로 이동 → 비식별 만족도 설문.
인기 탭: 유형별 입찰참가자 또는 경쟁률의 공표된 집계만 사용; 표본/기간 표시. 개별 공고의 현재 입찰자가 누락된 경우 '알 수 없음'.

## 5. 수익 모델 및 게이트
- Phase A 무료 정보 서비스로 SEO/품질/재방문 검증
- Phase B 자격 검토된 광고·협찬 또는 고급 분석 리포트 실험
- Phase C 실물 점검/운송 사업자 제휴: 광고/알선 경계를 법률 검토
- Phase D 경매대리/중개 수수료: 법적 자격, 계약, 소비자보호, 광고규제 외부 검토 후 별도 승인. 코드 플래그 기본 OFF.
- 경매 입찰을 로또처럼 묘사하거나 보장수익/긴박감 조작 UI를 사용하지 않는다.

## 7. 제외 범위
자동 입찰, 실시간 가격 예측, 근거 없는 낙찰차익 예측, 다크패턴 카운트다운, 유료 우선 노출의 미표기, 재산권리 확정 판단.

## 8. 미해결
공고별 이미지 이용권, 공식 링크 패턴, 최신 API 한도/필드, 낙찰결과의 유형별 분해 가능 여부, API 사용 승인, 법률 자문.
